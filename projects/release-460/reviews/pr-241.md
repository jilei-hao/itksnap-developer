## 1 · Verdict in plain words

The PR does two things:
1. It deletes the 2014 guard that stops ITK-SNAP from starting when the Windows user name is not ASCII.
2. It adds a manifest that switches the process code page to UTF-8.

**Deleting the guard is what fixes the reported bug**, and it fixes it on its own. The PR says the
opposite: that removing the guard "is not enough", because ITK's `itksys` decodes paths with the legacy
code page. That is not true: ITK 5.4.0 builds `itksys` with `CP_UTF8` (checked in its CMake). The 2014
guard's own commit message says "this seems to be fixed in ITK 4.5", which is most likely this same
setting. We also measured it: a PR binary **without** the manifest creates the settings folder under the
correct Unicode name.

**The manifest is still worth having, for a different reason.** It makes non-ASCII paths given on the
**command line** work (`-g`, `-s`, `-o`, `-w`, `--url`, double-clicking a file in Explorer). Before it,
`argv` arrives in the legacy code page and "日本" becomes "??". ITK-SNAP's own `DecodeFilename()`
(`main.cxx:439`) then fails in `GetLongPathNameA`, and the process **crashes silently** (0xC0000409,
measured). With the manifest, the same launch loads the image. The author mentioned the `argv` effect
in a later PR comment as a side effect. It is really the manifest's main effect.

So the asks are:
- correct the rationale in the commit message, the PR text and three code comments;
- point the test at what the manifest really changes;
- let Paul decide whether a process-wide code-page change is welcome in a PR titled as a user-name fix.

## 3 · Findings, most important first

### F1 — The stated mechanism is wrong (commit message, PR text, 3 comments)

The PR says that itksys converts narrow paths with `MultiByteToWideChar(KWSYS_ENCODING_DEFAULT_CODEPAGE, …)`
and that "ITK leaves that macro at its `CP_ACP` default". It also says that under a legacy code page
`MakeDirectory()` "silently creates a mis-named directory".

- ITK v5.4.0, `Modules/ThirdParty/KWSys/CMakeLists.txt:11` has `set(KWSYS_ENCODING_DEFAULT_CODEPAGE CP_UTF8)`
  ("Use Unicode instead of ASCII by default"). VTK does the same (`Utilities/KWSys/CMakeLists.txt:24`).
- T2 and T5 confirm it by behaviour: without the manifest, itksys creates the correct Unicode name.
- The CRT route, used by `Registry`, is covered in `ITK-SNAP.exe` by `setlocale(LC_ALL, ".UTF8")`
  (`main.cxx:1060`). The PR says so itself.

So in `ITK-SNAP.exe` the two routes already agreed, and the guard was the only obstacle. Wrong text
to fix:
- `Common/SystemInterface.cxx:93-95`: "Non-ASCII characters are supported because the application
  manifest … sets the process code page to UTF-8".
- `Utilities/Win32/itksnap.manifest:4-6`: "so that itksys and the narrow Win32 API decode … Without it,
  non-ASCII characters in %APPDATA% are misdecoded". The itksys and %APPDATA% parts are wrong. The
  narrow Win32 API part is right, and ITK-SNAP has a concrete case: `GetLongPathNameA` in
  `DecodeFilename()`, which every command-line path goes through (T8b vs T8d).
- `Testing/Logic/NonAsciiPathTest.cxx:87`: "The key check: a legacy code page still creates a
  directory, just a mis-named one".
- `CMakeLists.txt:1280-1281`: "needed for paths with non-ASCII characters". Right, but it should say
  *command-line* paths.
- The commit body of `33565796` and the PR description ("Removing it alone is not enough").

Why this matters: a future maintainer who reads these will believe the manifest protects the
settings folder, and may keep it, or drop it, for the wrong reason. A squash-merge with a corrected
message fixes the history part.

Related: the description also says "On Windows older than 1903 the setting is ignored and behaviour
is unchanged." That is not quite right. The guard is gone on every Windows version, so on builds before
1903 (for example Windows 10 LTSC 2019 = 1809), users with non-ASCII names now **can** start ITK-SNAP.
T5, which runs without the manifest, simulates that case, and there the settings folder works too. It is
a harmless change for the better, but it is a change.

### F2 — The test does not test the manifest's effect

- Its itksys checks pass with or without the manifest (T2).
- Without the manifest it fails only in the Registry checks. They fail because the test never calls
  `setlocale(LC_ALL, ".UTF8")`, as `main.cxx` does. That is a configuration `ITK-SNAP.exe` never runs in.
- It never calls the code the PR changed: `SystemInterface::GetApplicationDataDirectory()`, including
  its new overflow branch.

Suggested, cheap:
1. **Test `argv` and the `A` APIs**, which the manifest really changes:
   - give the test's non-ASCII base directory as a command-line argument from CTest (T6 shows this fails
     without the manifest), or have the test re-launch itself with a non-ASCII argument through
     `CreateProcessW`;
   - call `GetLongPathNameA` on the UTF-8 path. That is exactly what `DecodeFilename()` does to every
     command-line path.
2. On Windows, `Check(GetACP() == CP_UTF8, "the manifest set the UTF-8 code page")`. It is a one-line,
   precise diagnosis.
3. Test the changed function itself: set `APPDATA` with `SetEnvironmentVariableW` to a non-ASCII
   directory, then construct `SystemInterface` with a dummy delegate, as `IRISApplicationTest` does.
   Also set a 5000-character `APPDATA` to hit the new "too long" branch.
   (The W8 3 fix for `RemoteImageLoadTest` uses the same `APPDATA` redirect, and it is compatible.)

### F3 — Scope: a process-wide change inside a user-name fix

`activeCodePage` changes the encoding of **every** narrow API in the process:
- `argv` and `getenv`;
- the `A` Win32 functions;
- `QString::fromLocal8Bit` / `toLocal8Bit`;
- libssh, libcurl, GDCM.

Most of these become *consistent* with the UTF-8 strings ITK-SNAP already uses, so the change is an
improvement. The biggest one: opening a file with a non-ASCII path from the command line or Explorer
goes from a silent crash (T8d) to working (T8b). Other examples:
- `FlywheelRemoteImageSource.cxx:101` `getenv("USERPROFILE")`;
- `DeepLearningServerEditor.cxx:42` `qgetenv("PATH")`.

It still counts as "a change that alters existing behavior" and touches the command-line interface.
`CONTRIBUTING.md` asks for an issue first for both. The author flagged it honestly, but only in a
comment after opening the PR. Options for Paul:
- **(a)** keep it as one PR, retitled "Support non-ASCII user names and command-line paths on Windows",
  with the description fixed;
- **(b)** split it: guard removal plus return-value checks (tiny, fixes the reported bug everywhere),
  then the manifest as its own PR.

The one visible downside found: `LayerInspectorRowDelegate.cxx:969` decodes a child process's stderr
with `fromLocal8Bit`. The child still writes CP1252, so non-ASCII error text would show as mojibake.
This is cosmetic.

### F4 — `itksnap-wt` (and c3d/greedy) do not get the manifest

The author offers to add them. `itksnap-wt` ships to users and takes paths on the command line, so
it has the same `argv` problem. Giving it the manifest is one line in
`Utilities/Workspace/CMakeLists.txt`. Worth asking for in this PR. c3d and greedy are separate
repositories, so they need follow-ups upstream there. None of this is a regression: `itksnap-wt` never
calls `GetApplicationDataDirectory()`.

### F5 — Found on the way, not this PR's: a missing `-g` file crashes ITK-SNAP on Windows

`ITK-SNAP.exe -g C:\no\such\file.nii.gz` exits with 0xC0000409 and no message, on staging and so on
master too. The cause is in `DecodeFilename()` (`main.cxx:439-456`, WIN32 branch):
- `GetLongPathNameA` fails for a path that does not exist, and the function throws `IRISException`.
- It is called from `parse()`, before `main()`'s `try`, so the exception is uncaught and the CRT aborts.
- It also leaks `buffer`.

By reading the code (not run), macOS and Linux instead reach the normal "Failed to load image" dialog
at `main.cxx:1019`. A PR #241 without
the manifest would route **every** non-ASCII command-line path into this crash. This is a W8
candidate for our queue. It is independent of #241, and should not be asked of the author.

### F6 — Nits (non-blocking)

- `SystemInterface.cxx:105`: `n_chars` on overflow is the required buffer size **including** the null
  terminator, so the message reports one character too many.
- `SystemInterface.cxx:114`: the second `WideCharToMultiByte` return value is unchecked. It cannot
  realistically fail after the sizing call.
- `NonAsciiPathTest.cxx`: `Check` and `ExistsAccordingToNativeAPI` could be `static`, and the byte
  strings could be `static const char X[]`.
- `itksnap.manifest:6`: "adding … supportedOS entries would override what Qt configures". Qt
  configures DPI awareness through the API, not `supportedOS`. The dpiAware half is right.

## 5 · What the PR gets right

- It finds and explains the real 2014 origin of the guard. It also notices that the guard is an
  ASCII gate, not a failure check.
- It fixes two real unchecked returns in the same function:
  - `GetEnvironmentVariableW` overflow, which previously would have used an uninitialized buffer;
  - `WideCharToMultiByte` sizing.
- The manifest is minimal and correctly namespaced. It uses the same MSVC mechanism Qt uses for its
  own tools (`_qt_internal_generate_longpath_win32_rc_file_and_manifest`: "MSVC needs the manifest file
  as part of target_sources"), and it merges cleanly with the linker's default manifest (T4).
- The test checks results through the wide Win32 API, not through the API under test. That is the
  right instinct: it is why T2 could show what really fails.

## 6 · Interactions with our queue

  `add_test(NAME IRISApplicationTest …)`. The resolution is to keep both blocks. It merges cleanly with
