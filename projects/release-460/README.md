# release-460 — ITK-SNAP 4.6.0

Sprint directory for the 4.6.0 release, following the metronome convention
(`~/metronome/docs/sprint-workflow.md`).

## Files

| File | Lifetime | What it holds |
|---|---|---|
| [SPRINT_PLAN.md](SPRINT_PLAN.md) | the sprint | Scope, the eight workstreams, done-criteria, risks, cut line — plus §2, a dated snapshot of branch and dependency state. |
| [PROGRESS_LOG.md](PROGRESS_LOG.md) | append-only | One dated entry per session. Never rewritten. |
| [NEXT_SESSION_PROMPT.md](NEXT_SESSION_PROMPT.md) | one session | The ignition key. Rewritten wholesale at every `/handoff`. |
| [change_tracking.md](change_tracking.md) | the sprint | What has **merged** since v4.4.0, classified feature / bugfix / build / docs. Raw material for `ReleaseNotes.md`. |
| [MERGE_ORDER.md](MERGE_ORDER.md) | the sprint | **Merge order** of the topic branches, the measured constraints behind it, and a Status section regenerated by a git hook whenever a branch moves. Updated every time a branch changes (SPRINT_PLAN rule 3). |
| [branches.md](branches.md) | the sprint | The **review queue**: one row per topic branch that could become an upstream PR — commits, evidence, standalone test result, points for Paul. The planning-meeting handout. |
| [workstreams/](workstreams/) | the sprint | One spec per workstream. See its [README](workstreams/README.md) for why these are files rather than sub-projects. |

The first three names are fixed by metronome. `change_tracking.md` and `branches.md` are the
additions. They split from `SPRINT_PLAN.md` §2 along one line each: `change_tracking.md` holds
**merged** work, and `branches.md` holds work that is **branched and awaiting review**. Per-item
evidence lives in the workstream file that owns it; `branches.md` only maps items onto branches.

## Start ritual

1. Read [NEXT_SESSION_PROMPT.md](NEXT_SESSION_PROMPT.md).
2. **Ask Jilei which item this session is for.** No goal is preselected (SPRINT_PLAN rule 2).
3. Skim [SPRINT_PLAN.md](SPRINT_PLAN.md) for where that item sits. §2 goes stale fastest —
   re-verify it with §7 before trusting a branch count.
4. Only then touch code — on that item's own topic branch, never on `staging/v460` (rule 1).
5. If a branch changed, bring [MERGE_ORDER.md](MERGE_ORDER.md) to "Needs attention: nothing" before
   `/handoff` (rule 3).

End the session with `/handoff`.
